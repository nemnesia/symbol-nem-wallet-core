# symbol-nem-wallet-core コンセプトシート

## 1. 概要

- 一言で説明: symbol-nem-wallet-core は、Symbol / NEM 向けアプリケーションの秘密鍵処理をUIやアプリケーション本体から分離し、複数の実行環境で共通利用するためのRust製コアである。
- 背景: Symbol / NEM のウォレットや署名アプリケーションでは、秘密鍵の生成、保存、復号、署名などの高リスクな処理を扱う。既存の構想では、これらの処理がUIや実行環境ごとに分散し、秘密情報の残存、実装間の方式差異、レビュー対象の拡大につながる可能性がある。

本コンセプトは、秘密鍵を扱う責任を限定されたコアへ集約し、UIやアプリケーションが秘密鍵そのものを扱わない境界を定めるものである。具体的なAPI、データ形式、暗号方式、crate構成は本コンセプトでは決定しない。

## 2. 解決したい課題

- 対象者: Symbol / NEM 向けウォレット、署名アプリケーション、CLI、認証・SSO用署名クライアントなどを開発するソフトウェア開発者。
- 現在の課題: 秘密鍵処理がUIコードやアプリケーションロジックに混在し、Desktop、Android、iOSなどの実行環境ごとに分散する可能性がある。
- 課題の原因: 本文上の仮定として、秘密鍵をJavaScript側で扱う実装では、状態管理、グローバル変数、ログ、例外処理、デバッグ機能などに秘密情報が残るおそれがある。また、複数実装の間で暗号方式やデータ形式に差異が生じる可能性がある。
- 既存手段の不足: 現状の構想からは、UIと秘密鍵処理の責任を一貫して分離し、複数環境にまたがって同じ判断基準を適用する方法が確立しているか確認できない。
- 放置した場合の影響: 秘密情報の露出箇所や実装差異が増え、セキュリティレビューおよび保守の対象範囲が広がる可能性がある。

上記は本書で整理した課題と仮定であり、脅威モデルやリスク低減効果が検証済みであることを示すものではない。

## 3. 目的

1. UIやアプリケーション本体から秘密鍵処理を分離し、秘密鍵そのものをUIへ返さない責任境界を作る。
2. Desktop、Android、iOSなど異なる実行環境で、秘密鍵処理に関する共通の利用方針を適用できるコアを目指す。
3. 秘密鍵生成、鍵管理、署名などの高リスク領域を限定されたコードへ集約し、レビュー対象を把握しやすくする。
4. SymbolとNEMの双方を対象とする。ただし、両者に共通化できる処理の範囲は別途確認する。

## 4. 対象ユーザーと主要利用場面

### Symbol / NEM向けアプリケーション開発者

- 利用目的: ウォレットや署名を必要とするアプリケーションへ、秘密鍵を直接扱わない鍵処理の責任領域を組み込む。
- 前提知識: 対象アプリケーション、Symbol / NEM、秘密鍵を扱う責任分担に関する知識を持つことを想定する。必要な知識の範囲は未決定。
- 解決される課題: UIやアプリケーションごとに秘密鍵処理を実装する負担と、実装間の方式差異を抑える。

### 主要利用場面

- 誰が: Symbol / NEM向けウォレットまたは署名アプリケーションの開発者が。
- どのような状況で: アプリケーションから署名などの秘密鍵処理を利用する必要があるときに。
- 何に困っており: UIやアプリケーション側で秘密鍵を保持すること、または実行環境ごとに鍵管理処理を実装することに困っている。
- どのような状態になることを期待するか: アプリケーションが秘密鍵そのものを取得せずに、必要な秘密鍵処理を利用できる状態。

Desktop、モバイル、CLI、認証・SSOなどの候補のうち、v1で優先する利用場面は未決定である。一般利用者がこのコアを直接操作することは想定していない。

## 6. v1のスコープと責任境界

### v1で扱う範囲

v1では、Symbol / NEM向けアプリケーションから秘密鍵処理を分離し、秘密鍵をUIへ直接返さずに必要な署名処理を利用するコアの責任領域を検証する。一般的なウォレット利用を想定し、ニーモニックを用いたHD Wallet対応を予定している。HD Walletの導出パスは、現行のSymbol / NEMにおけるMainnet・Testnetの区分に合わせる。本文で主な領域として挙げられている鍵の取込み、管理、保存、署名、ロックのうち、どこまでをv1の必須能力とするかは未決定である。

Coreが担う範囲と、OSのセキュリティ機能、ハードウェアウォレット、外部署名者などへ委ねる範囲は、方式を決めずに責任境界として要件定義で具体化する。

### v1では実施しないこと

現時点で、v1として明示的に除外すると決定した項目はない。v1への採否が未決定の項目は、11章「未決定事項」に記載する。

### プロジェクトとして扱わないこと

本文で明示された非目的は次のとおりである。

- 完全なSymbol SDKのRust再実装
- REST API Client、WebSocket Client、ノード選択、Blockchain Explorer
- UIコンポーネント、Wallet UIそのもの
- Node.js代替実装
- 特定ウォレットアプリ専用のロジック

一般的なトランザクション構築、ブロック情報取得、ネットワーク通信などは、既存のTypeScriptライブラリやアプリケーション側の責任とする構想である。ただし、Core側に必要な最小限のSymbol / NEMプロトコル処理の範囲は未決定である。

### 外部へ委ねること

- UI / Application: 公開情報の表示、ユーザー操作、アプリケーション設定、ネットワーク通信など。
- 既存ライブラリまたはアプリケーション側: REST、WebSocket、ブロック情報取得、一般的なトランザクション構築など。
- OSや外部の署名・保管機能: 利用する場合のプラットフォーム固有の保管または署名機能。

上記の外部責任とCoreの責任の詳細、ならびに連携失敗時の扱いは未決定である。

## 7. 判断原則

### 秘密情報の露出を最小化する

- 原則: 秘密鍵をUIやアプリケーション側へ返さず、必要以上に複製・保持しない方向で判断する。
- 理由: 本コンセプトの中心価値が、秘密鍵処理の責任分離にあるため。
- 判断への適用: API、Binding、Provider、保存方式を検討するときに、UIへ秘密鍵を露出させる案を採用しない。

### 責任境界を明確にする

- 原則: Core、UI / Application、OS機能、外部署名者の責任を混同しない。
- 理由: Coreへ集約する責任と外部へ委ねる責任が混在すると、Trusted Coreの範囲を過大に解釈するため。
- 判断への適用: OS連携、Hardware Wallet、External Signer、Watch-onlyの採否と責任分担を整理するときに適用する。

### SymbolとNEMを暗黙に同一視しない

- 原則: 共通化を目指す場合でも、チェーンごとの差異と対象ネットワークを明示して判断する。
- 理由: 本文では双方を扱う方針は示されているが、共通化できる処理の範囲は未確認であるため。
- 判断への適用: プロトコル処理、署名種別、アカウントやネットワークの扱いを具体化するときに適用する。

### 実装方式をコンセプトで固定しない

- 原則: 暗号方式、データ形式、API、crate分割、Bindingなどは、根拠と責任範囲を確認した後続工程で決定する。
- 理由: コンセプトは課題、価値、境界を定める文書であり、実装設計を確定する文書ではないため。
- 判断への適用: 複数の実装案から選択するときは、本コンセプトの価値と境界に照らして後続工程へ引き渡す。

### 原則間の優先順位

原則間の優先順位と衝突時の具体的な判断基準は未決定であり、要件定義で定める。

## 8. 成功条件

- 対象アプリケーションが、UIへ秘密鍵を直接返さずに、v1で定めた秘密鍵処理と署名処理を利用できる。
- 秘密鍵を扱うCoreの責任範囲と、UI / Application、OS、外部署名者へ委ねる範囲を説明できる。
- 複数の実行環境を対象とする場合に、環境ごとに鍵管理処理を作り直さず共通の利用方針を適用できる。
- Symbol / NEM双方を対象とする範囲と、共通化しない差異を説明できる。
- 秘密鍵処理のコードを、UIや一般的なネットワーク機能から分離したレビュー対象として扱える。

具体的な評価方法、対象環境、対応機能、数値目標は未決定である。

## 9. 前提条件と主なリスク

### 前提条件

- Rustを実装言語とし、Tauri、ネイティブアプリ、CLIなど特定のUIフレームワークに依存しないポータブルなコアを目指す。これは本文上の構想であり、実現方式は未確認である。
- OSが提供するセキュリティ機能を利用できる場合は、Coreだけで全ての鍵保護を完結させず、外部機能との連携を検討する。
- REST、WebSocket、一般的なトランザクション構築などは、Core以外の既存ライブラリまたはアプリケーションが担う構想である。
- 「安全に保存できる」「秘密情報を速やかに除去できる」などの安全性に関する表現は、実装・要件・検証によって確認されるまでは未確認である。

### 主なリスク

- Symbol / NEM、複数のOS、複数の保管・署名方式、複数の署名種別を同時に対象にすると、v1のスコープが過大になる。
- Software Key、OSの保管機能、Hardware Wallet、External Signer、Watch-onlyを同じSigner Providerとして扱うと、保管方式と署名能力の違いを誤って隠蔽する可能性がある。
- BindingやOS連携を介することで、Coreだけでは秘密情報に関する全体の責任を完結できない可能性がある。
- 「同一のセキュリティモデル」「安全な暗号化」「秘密情報の明示的破棄」などの意味と判定基準が未定義である。
- 広いプラットフォーム対応を前提にすると、同一Coreの利用可能範囲や互換性を過大に約束する可能性がある。
