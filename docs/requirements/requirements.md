# symbol-nem-wallet-core 要件定義書

## 1. 概要

- 背景: Symbol / NEMウォレットでは、ニーモニック、秘密鍵、HD Wallet、Software Key、暗号化保存、ロック、署名などの秘密情報を扱う。これらの処理がUI / Applicationや実行環境ごとに分散すると、秘密情報の管理責任、実装差異、レビュー対象が不明確になる可能性がある。
- 目的: Desktop / MobileのSymbol / NEMウォレット向けに、秘密鍵の由来にかかわらずSoftware Keyの管理・署名をCoreへ集約し、UI / Applicationが秘密情報の継続的な管理・保存主体にならずに利用できる状態を実現する。
- 解決する課題: ニーモニックや秘密鍵の取込み後の管理責任がUI / ApplicationとCoreの間で曖昧になること、Desktop / Mobileで鍵管理方針が分散すること、Symbol / NEMおよびMainnet / Testnetの区別が曖昧になることを解消する。

本書は `docs/consept/concept-sheet.md` の確定方針を、仕様設計へ引き渡せる要件へ整理したものである。API、データ形式、暗号方式、保存形式、アーキテクチャ、Binding方式、内部処理は決定しない。

## 2. 対象範囲と責任境界

### 対象

v1では、次の責任領域を対象とする。

- Desktop / MobileのSymbol / NEMウォレットから利用するSoftware Key管理・署名Core。
- ニーモニックによるHD Walletの生成、復元、秘密鍵の導出およびアカウント導出。
- 外部から直接取り込んだ秘密鍵のSoftware Keyとしての管理。
- Core内で独立して生成した秘密鍵のSoftware Keyとしての管理。
- 上記のSoftware Keyに対する暗号化保存、ロック、アンロック、署名への利用、破棄。
- Symbol / NEMおよびMainnet / Testnetを区別した鍵・アカウント導出。
- 秘密鍵またはニーモニックの取込み時に、UI / Applicationがユーザー入力を一時的に仲介する場合の責任境界。
- 取込み後の秘密情報の管理責任をCoreへ集約し、Core管理下の秘密鍵を通常の処理結果としてUI / Applicationへ返さない責任境界。

HD Walletから導出された秘密鍵、外部から直接取り込まれた秘密鍵、Coreが独立して生成した秘密鍵は、すべてSoftware Keyとして扱う。ニーモニック自体を取込み後もCore管理下に保持するか、復元時だけ利用して保持しないかは `OPEN-005` で決定する。

### 対象外

次はv1の対象外とする。

- Hardware Walletとの連携
- External Signerとの連携
- OS Keychain、Secure Enclave、TPMなどOS固有の鍵保管機能との連携
- Watch-onlyアカウントの提供。Watch-onlyはSignerとは別の、署名能力を持たないアカウント利用形態である。
- SNIF連携
- CLI、署名専用アプリ、認証・SSO向けクライアントへのv1提供
- REST Client、WebSocket Client、ノード選択、Blockchain Explorer
- 一般的なトランザクション構築・シリアライズ
- UIコンポーネント、Wallet UIそのもの
- Node.js代替実装
- 特定ウォレットアプリ専用ロジック

### 外部へ委ねる責任

- UI / Application: アカウント選択、公開情報の表示、ユーザー操作、ウォレット固有の表示・設定。秘密鍵またはニーモニックの取込み時には、ユーザー入力を一時的に仲介する場合があるが、秘密情報の継続的な保存・管理主体とはしない。
- Network層: REST、WebSocket、announceなどのネットワーク通信。
- Transaction構築層: Transactionの生成とシリアライズ。

取込み後の秘密情報の管理責任はCoreが担う。Core管理下の秘密鍵は、通常の処理結果としてUI / Applicationへ返さない。具体的な受渡し方法、メモリ上の保持方法、消去方法は仕様設計で決定する。

## 3. 利用者と関係者

### 主な利用者

- Desktop / MobileのSymbol / NEMウォレット開発者

CLI、署名専用アプリ、認証・SSO向けクライアントの開発者は、v1の主な利用者および成功判定の対象外とする。

一般利用者がCoreを直接操作することは想定しない。ウォレット利用者の入力は、ウォレットのUI / Applicationを通じて取込み処理へ渡される場合がある。

### 関係者

- Wallet Core: Software Keyの生成、導出、取込み、保存、ロック、アンロック、署名利用、破棄を担う主体。
- UI / Application: ユーザー操作、アカウント選択、公開情報の表示、ウォレット固有の表示・設定を担う主体。取込み時の入力を一時的に仲介する場合がある。
- Network層: ネットワーク通信を担う外部主体。
- Transaction構築層: Transactionの生成・シリアライズを担う外部主体。
- 仕様・設計担当者: 本書の要件を満たす具体方式を決定する担当者。

## 4. 前提条件と制約

### 前提条件

- SymbolとNEMの双方を対象とする。ただし、共通化する処理とチェーン固有として扱う処理の範囲は `OPEN-001` で決定する。
- MainnetとTestnetを明示的に区別する。
- HD Walletの導出パスは、現行のSymbol / NEMにおけるMainnet / Testnetの区分に合わせる。具体的なパス値と参照バージョンは仕様設計で確認する。
- Rust製のポータブルCoreとして提供する構想を維持する。Desktop / MobileからCoreを利用するBindingの対象範囲は `OPEN-003` で決定する。

### 制約

- Software Keyの由来は、HD Walletからの導出、外部からの秘密鍵直接インポート、Core内での独立生成を含む。
- ニーモニックおよび秘密鍵の入力形式、バイト表現、検証方法、API、データ形式は本書で決定しない。
- 暗号方式、KDF、Vault形式、保存形式、メモリ上の保持方法、消去方法は本書で決定しない。
- Symbol / NEMおよびMainnet / Testnetを暗黙に同一視しない。
- Hardware Wallet、External Signer、OS固有の鍵保管機能、Watch-only、SNIFはv1の要件へ含めない。

## 5. ユースケース

### UC-001: ニーモニックからHD Walletとアカウントを利用する

- 利用者: Desktop / Mobileウォレット開発者
- 目的: ニーモニックからHD Walletを生成または復元し、対象チェーン・ネットワークに対応するアカウントを導出して利用する。
- 事前条件: 対象チェーン、ネットワーク、HD Walletのv1対象範囲が確定している。
- 期待結果: HD Walletから導出された秘密鍵がSoftware KeyとしてCore管理下で扱われ、アカウント選択や公開情報の表示はUI / Applicationが利用できる。
- 主な失敗条件: 対象外のチェーンまたはネットワーク、対応範囲外の入力、または要件を満たさない入力が成功結果として扱われない。

### UC-002: 秘密鍵を直接インポートする

- 利用者: Desktop / Mobileウォレット開発者
- 目的: 外部から入力された秘密鍵をSoftware KeyとしてCoreの管理下へ取り込む。
- 事前条件: 直接インポートを利用するウォレットの責任境界と対象範囲が確定している。
- 期待結果: UI / Applicationが入力を一時的に仲介する場合があっても、取込み後の秘密情報の管理責任はCoreが担い、取り込まれたSoftware Keyを保存、ロック、アンロック、署名利用、破棄の対象として扱える。
- 主な失敗条件: 取込みに失敗した秘密鍵が有効なSoftware Keyとして扱われない。Core管理下の秘密鍵が通常の処理結果としてUI / Applicationへ返されない。

### UC-003: Software Keyを生成・管理・署名利用する

- 利用者: Desktop / Mobileウォレット開発者
- 目的: Core内で独立したSoftware Keyを生成し、鍵の由来にかかわらず共通のライフサイクルで利用する。
- 事前条件: Software Keyのv1対象範囲と署名処理の範囲が確定している。
- 期待結果: Software Keyを暗号化保存、ロック、アンロック、署名への利用、破棄の対象として扱える。
- 主な失敗条件: ロック中または破棄後のSoftware Keyが、要件上許可されない署名利用の成功結果として扱われない。

### UC-004: Desktop / Mobileから共通の鍵管理方針を利用する

- 利用者: Desktop / Mobileウォレット開発者
- 目的: 実行環境ごとに秘密鍵処理を個別実装せず、共通Coreの責任範囲として利用する。
- 事前条件: Desktop / MobileからCoreを利用する範囲と責任境界が確定している。
- 期待結果: 同じ鍵管理方針をDesktop / Mobileから利用でき、UI / Application側で個別に扱う範囲とCoreへ集約する範囲を区別できる。
- 主な失敗条件: 環境ごとに異なる秘密鍵管理責任が必要となり、CoreとUI / Applicationの境界を説明できない。

## 12. 仕様設計への引継ぎ

### 確定した要件

- Desktop / MobileのSymbol / NEMウォレット向けSoftware Key管理・署名Coreをv1対象とする。
- ニーモニックによるHD Walletの生成、復元、秘密鍵導出、アカウント導出をv1対象とする。
- HD Wallet由来、直接インポート、独立生成の秘密鍵を、すべてSoftware Keyとして扱う。
- Software Keyの暗号化保存、ロック、アンロック、署名への利用、破棄をv1対象とする。
- Symbol / NEMおよびMainnet / Testnetを区別する。
- 取込み時のUI / Applicationによる一時的な入力仲介を許容し、取込み後の秘密情報の管理責任をCoreへ集約する。
- UI / Applicationを秘密情報の継続的な管理・保存主体とせず、Core管理下の秘密鍵を通常の処理結果として返さない。

### 確定した制約

- Hardware Wallet、External Signer、OS固有の鍵保管機能、Watch-only、SNIF、CLI、署名専用アプリ、認証・SSO向けクライアントはv1対象外とする。
- REST、WebSocket、ノード選択、Explorer、一般的なTransaction構築・シリアライズ、UI、特定ウォレットアプリ専用ロジックはCoreの責任外とする。
- HD Walletの導出パスは、現行のSymbol / NEMにおけるMainnet / Testnetの区分に合わせる。

### 仕様設計で決定する事項

- HD Walletの具体的な導出パスの値、対象チェーン・ネットワークとの対応表、参照バージョン。
- ニーモニックおよび秘密鍵の入力形式、検証方法、受渡し方法、データ形式。
- API、暗号方式、KDF、Vault形式、保存形式、メモリ上の保持方法、消去方法。
- ニーモニックを保持する場合の具体的な保存・ロック・破棄方式。
- CoreとDesktop / Mobileを接続するBindingの実装方式。
- 署名対象、署名結果および各処理結果の具体形式。

### 要件レベルの未決定事項

- `OPEN-001` から `OPEN-005` を要件として決定する。
